# Adversarial correctness pass — 2026-08-28 (@ b0443ad, site v2026-08-21.2)

Static analysis of app.js / level3.js / bzip2.js / volume3d.js / index.html. The Level III
decoder held against truncation/garbage/signed-read attacks (catch-to-null plumbing + subarray
clamps); no Leaflet layer leaks; no timer stacking; the optional-server probe/fallback contract
holds everywhere reached.

**All 8 findings FIXED same day (site v2026-08-28.1).**

## P2 — loadSatLoop mutates shared loop state BEFORE its stale-request guard
`app.js:849-857`. clearFrames() and the frameUrls/frameTimes pushes run before
`if (req !== loopReq) return;` — every sibling loader guards first. A slow /api/frames response
landing after a product switch removes the NEW loop's buffer layers, installs the sat frame
list with no buffers, then bails: imagery vanishes, PLAY/step/scrub dead, nothing self-heals
until a product change or ◉ LIVE.

**FIXED (v2026-08-28.1)**: the `req !== loopReq` guard is now the first statement of the
listP.then, before clearFrames()/pushes — identical placement to every sibling loader.

## P2 — Auto-refresh repaints the LIVE still over a paused/pinned loop frame (sat + MRMS)
`app.js:3090-3095` (refreshStill) + `:435-445` (showMrms). The rv/ca branches guard on
usingFrames; sat and mrms don't. Pin satellite to 09:00Z (or pause any sat/MRMS loop), wait
≤120 s → live imagery paints over the pinned frame while the stamp still claims the archive
time (MRMS also overwrites #stamp). Silently wrong data labeled as archive; heals only on PLAY.

**FIXED (v2026-08-28.1)**: sat branch is now `if (!usingFrames) showSat(...)` and mrms is
`if (!usingFrames) refreshMrms(...)` — same polarity as the ca branch (rv already returned).

## P2 — Warning→cell merge has no severity precedence
`app.js:1820-1839` (renderStorm). The second warning within 40 km unconditionally overwrites
glyph/cls/threat/event (and nulls hail/wind). alerts/active is newest-first, so an older
FFW/SVR processed after a TOR wins: the cell's ▼ TOR marker and "Tornado Wrn" table row
silently become flood/SVR — on the signature storm-attribute feature. (Polygon and Alerts tab
still show the TOR, which is why live testing missed it.)

**FIXED (v2026-08-28.1)**: explicit rank (Tornado/observed-TVS 3 > SVR 2 > FFW/other 1 > bare
cell 0) kept in `target._warnRank`; glyph/cls/threat/event — and area/expires/_poly, so the row
stays coherent with the glyph that won — only change when the incoming warning ranks strictly
higher. hail/wind now merge only when non-null (a real tag is never nulled by a warning that
lacks one; a non-null incoming value still updates).

## P3 — Warning-only rows render "undefined" in the Dir column
`app.js:1933` with `:1827/:1837`. Rows without eventMotionDescription (FFWs commonly) and
without a merged cell (standalone, or below TRACK_MIN_ZOOM where EVERY row is standalone)
emit r.dir with no null-guard — the only column missing one.

**FIXED (v2026-08-28.1)**: `(r.dir || "—")` — em-dash when missing, like every sibling column.

## P3 — Warning fetch has no last-good fallback, and chimeCheck resets the seen-set on failure
`app.js:1690-1693` + `:3127-3141`. One routine api.weather.gov 503 → renderStorm([]) clears all
warning polygons and blanks the table ("No active severe warnings") for up to 120 s during
active weather — a false all-clear — and seenWarnIds collapses so the next success re-chimes
every old warning. The alerts-tab feed already has exactly the last-good treatment.

**FIXED (v2026-08-28.1)**: `lastWarnFeatures` keeps the last SUCCESSFUL fetch; !r.ok/network
failures now reuse it (fetchAllAlertsNational's pattern). warnP resolves {features, fresh};
renderStorm only runs chimeCheck when fresh — seenWarnIds is never rebuilt off a failed fetch.

## P3 — showSiteInfo innerHTML sink missed by the 2026-08-21 XSS round
`app.js:1514`. s.id/s.net/name interpolated unescaped; the SAME strings are esc()'d at the
tooltip (:1533) and popup (:1540) with the rationale "id/name are API-fed". Runs at boot for
the current selection.

**FIXED (v2026-08-28.1)**: `esc(s.id)` / `esc(s.net)` (the only strings this sink interpolates;
lat/lon are toFixed numbers), matching the tooltip/popup siblings.

## P3 — loadAlerts / loadMetar lack request-generation guards
`app.js:2212-2222` / `:2811-2839`. Pan A (slow) → pan B (cache instant) → A's response lands,
replaces alertsCache with the wrong-bbox list and re-renders — thinned/empty alerts until the
next moveend or refresh. Self-healing, hence P3.

**FIXED (v2026-08-28.1)**: `alertsReq`/`metarReq` generation counters (loopReq pattern). A stale
loadAlerts completion neither renders nor writes/clears alertsCache (the fetchers take the req
and compare before every cache touch); a stale loadMetar completion returns before painting.

## P3 (hardening) — no decompression output cap
`level3.js:272-280` + `bzip2.js:43-64,292-298`. bzip2/pako output is unbounded (~51×/block,
~1000×): a poisoned response from the pinned bucket could OOM the tab. Defense-in-depth for a
"every byte hostile" decoder; not an active bug.

**FIXED (v2026-08-28.1)**: 64 MB caps both sides. level3.js `_inflate` now uses chunked
`pako.Inflate` with an onData total counter (cap applies DURING decode, throw → existing
catch → raw-data path → decode null, same as a truncated stream). bzip2.js `MAX_OUT` throws
from simple()'s multi-block accumulation and from decompress()'s RLE grow loop (legit blocks
top out ~46 MB) — both land in decodeReflectivity's existing catch-to-null.
